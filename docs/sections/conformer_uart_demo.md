# Conformer UART file demo (Dedicated SRAM 256 KiB)

This optional mode keeps the model resident and accepts one WAV upload per
PowerShell invocation. The default `asr_INPUT_MODE=STATIC` retains the existing
static-sample inference test. The demo requires MPS4 SSE-320 FPGA or FVP, ExecuTorch,
U85-1024, Dedicated SRAM with 256 KiB cache, UART stdout, and CPU profiling.
Shared SRAM is not supported by this first version.

## Build and package

From the repository root, supply the existing PTE matching the hardware and cache:

```powershell
./scripts/windows/build-conformer-uart-demo.ps1 `
    -ModelPath <dedicated-256k.pte> -Package
```

The default build is `build/asr-uart/dedicated-256k`. The default package is
`build/board-test-packages/asr-uart/dedicated-256k.zip`; flash its SOFTWARE images
and images.txt following the package README. The model and quantization remain
unchanged. FPGA display plotting is disabled. No HAL or dependency sources are modified.
The package includes the sender and its helpers in `host/`, plus `UART_DEMO.md`;
all are covered by the package checksums. The sender can also run from that folder.
The existing static sample resources may still be generated by the common build,
but UART mode does not use those samples for recognition.

`-BaudRate` defaults to 115200 (8N1, no flow control). The build and sender accept
460800 and 921600 for later hardware validation; selecting a higher rate does not
establish that the board/USB serial bridge supports it reliably. Sender and firmware
must use the same rate.

## Send one file

Close MobaXterm or any other process using the same COM port. Discover ports with
`[IO.Ports.SerialPort]::GetPortNames()`. After resetting the programmed board:

```powershell
./scripts/windows/send-asr-audio.ps1 -Port COM5 `
    -WavPath "C:\audio\hello.wav"
```

The script checks the container and sends PCM bytes, not the WAV header. It accepts
RIFF/WAVE PCM format 1, mono, 16000 Hz, signed 16-bit samples. `fmt ` and `data`
chunks are located explicitly, with unknown chunks and odd chunk padding handled;
the header need not be 44 bytes. There is no implicit resampling, normalization or
truncation. Files must contain 512..480000 samples (32 ms..30 seconds). Float, stereo, compressed
or WAVE_FORMAT_EXTENSIBLE files are rejected with an error.

Format checking without opening a serial port:

```powershell
./scripts/windows/send-asr-audio.ps1 -WavPath "hello world.wav" -ValidateOnly
```

On success the sender prints these fields, with measured values:

```text
File: hello world.wav
Text: <recognized text>
NPU.Driver: <milliseconds> ms
End-to-end: <milliseconds> ms
Upload.UART: <milliseconds> ms
Request.Wall: <milliseconds> ms
```

NPU.Driver sums elapsed CPU-clock time around all synchronous Ethos-U driver calls;
it includes submission, cache maintenance, waiting and completion, not only pure
NPU compute. End-to-end is the continuous board interval from immediately before
preprocessing until immediately after postprocessing. It includes quantization,
invoke overhead, dequantization and decoding, and excludes upload, waiting for a
request, model initialization, display and result printing. Lazy initialization
inside the processing functions remains included. Consequently the first request
can differ from later requests. Times are returned in integer microseconds and
displayed as milliseconds. The UI does not print the six detailed timing stages.

Upload.UART is measured by the host from sending the request header until receipt
of the final PCM block ACK. It includes header/READY exchange, PCM transfer, ACKs
and host scheduling delays, but excludes connection setup, initial HELLO handshake
and inference. It is not a measurement of pure UART wire occupancy. Request.Wall
uses the same start and ends on receipt of the complete result line, so it includes
upload, processing, result transmission and host delays. It excludes WAV loading,
connection setup and the initial HELLO handshake. Neither changes the meaning of
End-to-end. A cached replay reports zero upload time. For FVP the field is named
Upload.TCP; host wall times and target simulated times must not be added together.

At 115200 baud with 8N1, PCM alone takes about 2.778 seconds per second of 16 kHz
mono PCM16 audio (32000 bytes/s times 10 bits/byte divided by 115200 bits/s).
Thus 7.022 seconds requires at least 19.505 seconds for PCM; ACKs and scheduling
increase the measured upload duration. This explains why upload can dominate.

Execute the command again with another file without resetting or rebuilding.
This is file-at-a-time recognition, not incremental streaming transcription.

## Long files: upload once, decode on the target

The host uploads every PCM sample once, and the target verifies the entire CRC
before starting recognition. The 30-second PCM buffer occupies 960000 bytes in
DDR. The 256 KiB NPU cache and the existing PTE remain unchanged. Short files up
to 112352 samples retain the existing single-inference decoding behavior.

Longer files use windows of 112352 samples (700 Mel frames, 7.022 seconds), with
a hop of 79360 samples (496 Mel frames, 4.96 seconds). Middle windows retain output
rows [25,149), or 124 rows. The first window retains its left edge, and the last
retains its valid right edge, excluding outputs beyond the actual unpadded feature
length. The two stride-2 kernel-3 subsampling convolutions determine the exact
global output grid. Cropped frame-level argmax paths feed one continuous CTC
decoder: duplicate state survives window boundaries and blank resets it. The
SentencePiece markers are converted only after all windows have been processed.
No text-level overlap removal is used. A new file starts a fresh decoder.

NPU.Driver is the sum over all windows. End-to-end is one continuous interval
covering every window's preprocessing, inference and output merging. No upload
or UART printing occurs inside that interval. The host still receives one final
text/result per file, and the previous successful full-file result is replayable.

The overlapping context is an approximation for this offline attention model;
it does not guarantee full-context equivalence. Validate boundary accuracy on
representative long recordings. The 30-second upload limit and the 7.022-second
model window are independent. A sender checks the advertised target capacity
before uploading, so old 7.022-second firmware rejects long files immediately.

## FVP upload loop

The PTE is shared with the FPGA build, but the AXF must be rebuilt for FVP. In
Windows PowerShell at the repository root:

```powershell
./scripts/windows/build-conformer-uart-demo.ps1 -Target FVP `
    -ModelPath <dedicated-256k.pte>
./scripts/windows/run-conformer-uart-fvp.ps1
```

The default FVP build directory is `build/asr-uart/dedicated-256k-fvp`. The runner
uses the installed Windows SSE-320 FVP; override `-FvpExecutable` if necessary.
Keep that PowerShell open. In a second PowerShell:

```powershell
./scripts/windows/send-asr-audio.ps1 -TcpHost 127.0.0.1 -TcpPort 5000 `
    -TimeoutSeconds 600 -WavPath "C:\audio\hello.wav"
```

Repeat the sender with another WAV without restarting FVP. Stop FVP with Ctrl+C.
Use exactly one of `-Port` and `-TcpHost`. `-BaudRate` configures a physical COM
port only; it does not throttle TCP or emulate USB serial transfer time. Check
the actual UART0 listening port printed by FVP; `-TcpPort` requests a starting
port and FVP can choose another if it is occupied. Reconnecting may also change
the listening port. No Telnet client is needed: the runner explicitly selects
raw mode so PCM values such as 0xFF and 0x0D are not interpreted or translated.

FVP builds enable the existing 320x240 HDLCD framebuffer, and both runners open
the LCD visualization while keeping the simulated board exterior hidden. Rebuild
with `-Target FVP` after upgrading an older display-disabled build. The LCD shows
Ready, Receiving, Processing, then the decoded text and simulated NPU.Driver and
Processing times. Processing is the same interval as the sender's End-to-end.
Text wraps at word boundaries across up to eight visible lines; longer results
show the last page with a notice, while UART retains the complete transcript.
The display does not show the WAV filename or host upload timing because those
are not sent to the target by protocol version 1. A new upload replaces the old
screen, and no screen refresh occurs per PCM block or inside processing timing.
The final UART result is emitted before drawing the result screen.

This display feature is compiled only for the FVP UART mode. FPGA builds retain
display-disabled operation and the same UART result format. Native Windows FVP
provides the GUI directly; WSL use also requires a working GUI environment such
as WSLg. The framebuffer uses the existing configured HDLCD memory region.

The provided runner is functional fast mode (`--fast`, timing adapter disabled).
NPU.Driver and End-to-end remain simulated target intervals, not FPGA performance
measurements. Upload.TCP and Request.Wall are real host elapsed times, but are not
predictions of COM-port upload time. The host response timeout can be extended
up to 86400 seconds. No FPGA package is generated with `-Target FVP`.

FVP disables the firmware inter-byte receive deadline: simulated CPU time is not
a reliable deadline for host-paced TCP input. `-TimeoutSeconds` still controls
the host's response wait in real elapsed time. If an upload is interrupted or
the sender exits mid-payload, restart FVP before submitting a new request; the
receiver cannot distinguish a new header from unfinished binary PCM. Physical
FPGA firmware retains its two-second inter-byte timeout.

Alternatively launch the same FVP build in WSL from the repository root:

```bash
bash scripts/run_conformer_uart_fvp.sh
```

Set `FVP_PATH` to override the Linux FVP executable. This runner loads its vendor
runtime environment when available. The Windows sender may connect using WSL
localhost forwarding; if that is unavailable, use the WSL address reachable from
Windows as `-TcpHost`. The native Windows runner avoids this forwarding dependency.

## Wire protocol version 1

The protocol uses the same UART for binary input and ASCII responses. The MPS4
application adapter reads the CMSDK DATA/STATE registers through the generated
`uart_config.h` address. It deliberately does not call `UartGetc()`, whose text
CR-to-LF translation would corrupt PCM. Timeout polling is contained in the ASR
application, with no new HAL API or change under `source/hal/source`.

1. Host sends `?`; an idle board replies `ASR_HELLO 1 16000 480000 512`.
2. Host sends a 16-byte header: ASCII `ASR1`, uint32 request ID, uint32 sample
   count, uint32 CRC32 of PCM. Integers and PCM16 are little-endian.
3. Board validates length and replies `ASR_READY <id>`.
4. Host sends up to 512 PCM bytes, then waits for `ASR_ACK <id> <total-bytes>`.
   The last block may be shorter. No block is automatically retransmitted.
5. After complete payload reception and CRC verification, board runs inference.
6. Board replies `ASR_RESULT <id> <npu-us> <end-to-end-us> <text>`.

CRC is CRC32/ISO-HDLC (reflected polynomial 0xEDB88320, initial and final XOR
0xFFFFFFFF). The FPGA receiver has a two-second inter-byte timeout for incomplete
headers/payloads and returns to header scanning after errors. FVP disables this
simulated-time deadline as described above. The receiver emits
`ASR_ERROR <id> LENGTH|CRC|TIMEOUT|INFERENCE|REQUEST_ID` where applicable.
After an interrupted upload, allow its receive timeout to expire before retrying.
The new command then performs a fresh handshake.

The most recent successful request ID/sample count/CRC and result are cached.
Repeating that exact header returns the cached result without upload/inference;
reusing the ID with different metadata is rejected. This is last-request replay
protection for one boot, not persistent job storage. The sender generates a new
ID for each command and never automatically retries inference after an uncertain
timeout. Both sides assume a single host and at most one outstanding request.

The bounded PCM buffer is `480000 * 2 = 960000` bytes in the existing DDR `ifm`
section. Its address must be checked in the produced map; it must not consume
the independent 256 KiB SRAM cache or overlap the fixed temporary allocator.

## Verification

```powershell
./tests/processing/asr/Test-AsrUartSender.ps1
./tests/processing/asr/Test-AsrTcpTransport.ps1
```

Host tests use generated WAV containers and a simulated serial connection to
check metadata, format rejection, byte preservation, CRC, partial final blocks,
ACK pacing, replay, and failure/timeout behavior. Native ASR CTest also includes
`asr-uart-protocol`. These do not replace FPGA validation of clock, UART overrun,
actual received bytes, repeated recognition and timestamps. Firmware build and
packaging alone are not a board execution pass.
The TCP test uses a real loopback connection to check all byte values, preserving
partial lines across read timeouts, and detecting a closed peer connection.
